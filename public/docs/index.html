Documentation

FlowMember works entirely through data-ms-* attributes in Webflow's Designer — no custom code required for the common cases. This page covers every attribute the SDK supports, what it does, and how to use it.

Getting started

One script tag on your Webflow site, then everything else is attributes.

In your Webflow project: Site Settings → Custom Code → Footer Code (site-wide), or a single page's Page Settings → Before </body> tag. Paste your embed snippet — copy the exact one from your site's dashboard, it already has your site's key filled in:

HTML
<script src="https://YOUR-SERVER/sdk/flowmember.js"
        data-site-id="YOUR_PUBLIC_KEY"
        data-api="https://YOUR-SERVER"></script>
AttributeOnRequiredDescription
data-site-idthe <script> tagYesYour site's public key, from the dashboard's embed code. Scopes every request to your site — visitors on other FlowMember sites never mix with yours.
data-apithe <script> tagNoThe FlowMember server URL. If omitted, it defaults to wherever the script itself was loaded from — safe to leave out if you're pasting the snippet exactly as copied.
Note Once the script tag is in place, every attribute below just works anywhere on the page — no extra setup per element.

Signup & login forms

Mark a Webflow form as a signup or login form and FlowMember wires up the submit handler for you.

HTML
<form data-ms-form="signup">
  <input type="email" name="email" required>
  <input type="password" name="password" required>
  <button type="submit">Sign up</button>
</form>

<form data-ms-form="login">
  <input type="email" name="email" required>
  <input type="password" name="password" required>
  <button type="submit">Log in</button>
</form>

The SDK looks for an input named email and one named password inside the form. If Webflow left both inputs with the same name (a common Designer slip), it falls back to matching by type="email" / type="password" — so it's forgiving of minor markup mistakes, but the two fields must still resolve to different elements.

Attribute reference

AttributeOnValueDescription
data-ms-forma <form>, or a wrapper <div> around onesignup or loginMarks the form as an auth form. Works on a Webflow Form Block's wrapper div too — the SDK looks inside for the real <form> automatically.
data-ms-redirectthe same <form>a URL or pathWhere to send the visitor after a successful signup/login. Omit it and the page just reloads in place.
data-ms-errorany element inside the form (optional)—Where error text (e.g. "Invalid email or password") is written. If you don't add one, FlowMember creates a small red text element inside the form automatically.
Webflow tip FlowMember intercepts the submit before Webflow's own handler runs, so Webflow's built-in "Thank you" message and form storage are skipped for these forms — that's expected, the member record is stored in FlowMember instead.

Logging out

Turn any link or button into a logout action.

HTML
<a href="#" data-ms-logout>Log out</a>
AttributeOnValueDescription
data-ms-logoutany clickable element— (presence only)Clears the visitor's session and redirects. Clicking prevents the link's default behavior, so href="#" is fine.
data-ms-redirectthe same elementa URL or pathWhere to send the visitor after logging out. Omit it and they stay on the current page (refreshed to its logged-out state).

Show & hide by auth state

Reveal or hide elements based on whether the visitor is logged in — for banners, nav items, or "members only" sections.

HTML
<div data-ms-content="member">Welcome back!</div>
<div data-ms-content="visitor">Sign up to get started</div>
AttributeValueDescription
data-ms-contentmemberVisible only when a member is logged in.
data-ms-contentvisitorVisible only when no one is logged in.
Not a security boundary This only hides elements with CSS — the markup and its contents are still present in the page source. Anyone can inspect the page and see hidden content. For anything that actually needs to stay secret from non-qualifying visitors, use gated content instead, which fetches the real content from the server only when allowed.

Show & hide by plan

Reveal an element only to members on a specific plan.

HTML
<div data-ms-plan="pro">This is a Pro-only perk.</div>
AttributeValueDescription
data-ms-plana plan name, e.g. free or proVisible only if the logged-in member's plan exactly matches this value. Hidden for visitors and for members on a different plan.

A member's plan is set per-site by the site owner from the dashboard's Members panel. Same CSS-only caveat as above applies — pair with gated content for anything that must stay actually hidden.

Data binding

Print a logged-in member's own info into the page.

HTML
Logged in as <span data-ms-bind="email"></span>
Your plan: <span data-ms-bind="plan"></span>
AttributeValueDescription
data-ms-bindemail, plan, or idFills the element's text with that field from the logged-in member. Empty for logged-out visitors.

Gated content

The real security boundary — content is only ever sent to the browser if the member's plan qualifies.

Create a content block from your site's dashboard (Members → Gated Content), give it a key and the plan required to see it. Then reference that key on your page:

HTML
<div data-ms-protected="premium-article" data-ms-fallback="upgrade-msg"></div>
<div id="upgrade-msg" style="display:none">Upgrade to read this.</div>
AttributeOnValueDescription
data-ms-protectedany elementthe content block's keyFetches that block from the server and fills the element's HTML with it — but only if the visitor's plan is allowed. If not, the element stays hidden and the actual content is never sent to the browser at all.
data-ms-fallbackthe same elementan element's idShown instead when the visitor doesn't qualify (e.g. an upgrade prompt). That element should start with style="display:none" so it's hidden until needed.
Why this is different Everything else on this page (data-ms-content, data-ms-plan) hides elements client-side — the content is technically still in the page. Gated content is fetched from the server per-request and checked against the member's plan there, so non-qualifying visitors' browsers never receive it in the first place.

JavaScript API

For custom interactions beyond what attributes cover, a small window.FlowMember object is always available.

JavaScript
FlowMember.isLoggedIn()   // true / false
FlowMember.getMember()    // { id, email, plan } or null
FlowMember.logout()       // clears the session in place (no redirect)

Useful inside a Webflow page's custom "before </body>" script, or an Embed element, for logic the attributes above don't cover.

Member dashboard

A ready-made account page for your members — nothing to build.

Every site gets a self-service dashboard where members can log in, see their plan, and see which gated content they currently have access to. Copy the link from your site's dashboard (Members → Member dashboard link) and add it to your Webflow nav, e.g. as "My Account":

URL
https://YOUR-SERVER/member?site=YOUR_PUBLIC_KEY

This is a separate page (not attribute-based) that FlowMember hosts and maintains for you — no design or build work required.

Full example

Everything above combined into one page.

HTML
<!-- once per page, usually in Footer Code -->
<script src="https://YOUR-SERVER/sdk/flowmember.js"
        data-site-id="YOUR_PUBLIC_KEY"></script>

<!-- nav -->
<div data-ms-content="visitor">
  <a href="/login">Log in</a>
</div>
<div data-ms-content="member">
  Hi, <span data-ms-bind="email"></span>
  <a href="#" data-ms-logout data-ms-redirect="/">Log out</a>
</div>

<!-- login page -->
<form data-ms-form="login" data-ms-redirect="/dashboard">
  <input type="email" name="email" required>
  <input type="password" name="password" required>
  <button type="submit">Log in</button>
</form>

<!-- gated article -->
<div data-ms-protected="q4-report" data-ms-fallback="q4-locked"></div>
<div id="q4-locked" style="display:none">
  <div data-ms-plan="pro">Hmm, this shouldn't happen on Pro.</div>
  Upgrade to Pro to read the full report.
</div>
